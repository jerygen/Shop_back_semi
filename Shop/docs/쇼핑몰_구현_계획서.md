# 쇼핑몰 개인 프로젝트 구현 계획서

## 1. 구현 개요

본 구현 계획은 Spring Boot 기반 쇼핑몰 백엔드 프로젝트를 대상으로 한다. 현재 프로젝트에는 Maven, Spring Data JPA, Spring Security, JWT, Swagger 설정과 `User` 도메인 일부가 선행 구현되어 있으므로, 이를 기반으로 상품, 주문, 장바구니, 관리자, 채팅 기능을 단계적으로 확장한다.

## 2. 기술 스택

| 구분 | 기술 |
|---|---|
| Language | Java 21 |
| Framework | Spring Boot, Spring Web MVC |
| Persistence | Spring Data JPA, Hibernate |
| Database | MySQL |
| Security | Spring Security, JWT |
| API 문서 | springdoc-openapi Swagger UI |
| Realtime | WebSocket + STOMP |
| Build | Maven |
| Test | JUnit, Spring Boot Test, Security Test |

## 5. 도메인 구현 계획

### 5.1 User

- 현재 `User` 엔티티를 기준으로 진행한다.
- ERD의 `userPassword`와 코드의 `password` 명칭 차이를 정리한다.
- `role`은 `ROLE_USER`, `ROLE_ADMIN` 형식으로 저장하는 것을 권장한다.
- 회원가입은 제외 범위이므로 `data.sql` 또는 초기화 로직으로 테스트 계정을 생성한다.

### 5.2 Product

- 필드: `productNo`, `productId`, `productName`, `productPrice`, `stock`, `description`, `regDate`
- 주요 검증:
  - 가격은 0보다 커야 한다.
  - 재고는 0 이상이어야 한다.
  - 상품 ID는 중복될 수 없다.
- 관리자 등록/수정/삭제와 고객 조회 기능에서 공통으로 사용한다.

### 5.3 Cart

- 필드: `cartNo`, `user`, `product`, `quantity`
- 사용자와 상품 조합은 유일해야 한다.
- 동일 상품을 다시 담으면 신규 행을 만들지 않고 수량을 합산한다.
- 주문 완료 후 해당 사용자의 장바구니를 비운다.

### 5.4 Orders / OrderLine

- `Orders` 필드: `orderNo`, `user`, `orderDate`, `address`, `totalAmount`
- `OrderLine` 필드: `orderLineNo`, `order`, `product`, `unitPrice`, `quantity`, `amount`
- 주문 생성은 트랜잭션으로 처리한다.
- 주문 당시 가격을 `unitPrice`에 저장하여 이후 상품 가격 변경의 영향을 받지 않도록 한다.
- 재고 부족 시 주문 전체를 실패 처리한다.

### 5.5 ChatRoom / ChatMessage

- `ChatRoom` 필드: `chatRoomNo`, `customer`, `admin`, `regDate`
- `ChatMessage` 필드: `chatMessageNo`, `chatRoom`, `sender`, `message`, `regDate`
- 고객은 본인의 채팅방만 생성/조회할 수 있다.
- 관리자는 전체 채팅방 목록을 조회할 수 있다.
- 메시지는 발신자와 채팅방 참여 권한을 검증한 뒤 저장한다.

## 8. 보안 구현 계획

- `GET /api/products`, `GET /api/products/{productNo}`, `/login`, Swagger 경로는 `permitAll`로 설정한다.
- 고객 API는 `hasRole("USER")`, 관리자 API는 `hasRole("ADMIN")`으로 제한한다.
- JWT 필터에서 토큰 만료, 서명 검증 실패, 누락 토큰을 구분해 처리한다.
- WebSocket 연결 시에도 JWT 인증을 적용한다.
- 로그아웃은 서버 상태를 두지 않는 JWT 방식의 특성상 클라이언트 토큰 삭제를 기본 정책으로 한다.

## 9. 트랜잭션 및 정합성 계획

- 주문 생성, 장바구니 주문, 재고 차감은 `@Transactional`로 묶는다.
- 장바구니 주문 시 모든 상품의 재고가 충분한 경우에만 주문을 생성한다.
- 주문 상세 금액은 `unitPrice * quantity`로 계산한다.
- 주문 총액은 주문 상세 금액 합계로 계산한다.
- 매출 통계는 `OrderLine` 기준으로 집계한다.

## 10. 예외 처리 계획

| 상황 | HTTP Status | 예외 메시지 예시 |
|---|---|---|
| 인증 실패 | 401 | 로그인이 필요합니다. |
| 권한 없음 | 403 | 접근 권한이 없습니다. |
| 상품 없음 | 404 | 상품을 찾을 수 없습니다. |
| 주문 없음 | 404 | 주문을 찾을 수 없습니다. |
| 채팅방 없음 | 404 | 채팅방을 찾을 수 없습니다. |
| 재고 부족 | 409 | 상품 재고가 부족합니다. |
| 장바구니 비어 있음 | 400 | 장바구니에 상품이 없습니다. |
| 입력값 오류 | 400 | 요청 값을 확인해 주세요. |

## 14. 구현 시 주의사항

- `UserRepository`의 `findById(String id)`는 JPA 기본 `findById(Long id)`와 혼동될 수 있으므로 `findByUserId` 같은 명칭으로 정리하는 것을 권장한다.
- ERD의 `Users`, `Products`, `Order_Line` 등 테이블명과 JPA 엔티티명/필드명을 명확히 매핑한다.
- `Orders`는 SQL 예약어와 혼동될 수 있으므로 테이블명 지정 여부를 검토한다.
- JWT 만료 시간이 현재 10분으로 설정되어 있으므로 테스트 편의와 보안 요구 사이에서 조정한다.
- WebSocket 인증은 HTTP Security와 별도로 연결 단계 인터셉터 검증이 필요하다.
- 상품 삭제는 이미 주문된 상품과의 관계를 고려해 물리 삭제 대신 판매 중지 필드를 둘지 검토한다.

## 15. 완료 기준

- 모든 요구사항 ID가 API 또는 구현 정책에 매핑되어 있다.
- Swagger에서 고객/관리자 대표 시나리오를 모두 재현할 수 있다.
- 주문 생성 시 주문, 주문 상세, 재고가 일관되게 반영된다.
- 채팅 메시지가 실시간 전달되고 DB에 저장된다.
- 인증/인가 실패 케이스가 명확한 HTTP Status와 메시지로 응답된다.
