# 쇼핑몰 개인 프로젝트 구현 계획서

## 1. 구현 개요

본 구현 계획서는 현재 `Shop` Spring Boot 백엔드 프로젝트의 실제 구현 상태를 기준으로 정리한다. 프로젝트는 API 기반 쇼핑몰 백엔드를 목표로 하며, 프론트엔드는 별도 구현하지 않고 Swagger UI와 테스트 코드로 주요 흐름을 검증한다.

현재 프로젝트에는 회원가입, 로그인, JWT 인증, 공통 응답/예외 처리, 상품 조회, 단건 주문, 주문 내역 조회, 장바구니 담기/조회/장바구니 주문의 기본 흐름이 구현되어 있다. 관리자 기능과 채팅 기능은 계획에는 포함되어 있으나, 현재 코드 기준으로는 아직 본격 구현 전 단계다.

## 2. 기술 스택

| 구분 | 기술 |
|---|---|
| Language | Java 21 |
| Framework | Spring Boot 4.0.6, Spring Web MVC |
| Persistence | Spring Data JPA, Hibernate |
| Database | MySQL 8.4 |
| Security | Spring Security, JWT |
| API 문서 | springdoc-openapi Swagger UI |
| Build | Maven Wrapper |
| Test | JUnit, Spring Boot Test, Security Test |
| Infra | Docker Compose, Terraform 초안 |

참고 사항:

- `pom.xml`에는 Kotlin 의존성과 Kotlin Maven 플러그인이 포함되어 있으나, 현재 소스는 Java 중심으로 작성되어 있다.
- 테스트는 사용자의 작업 방식에 맞춰 IntelliJ 내부에서 실행하는 것을 기준으로 한다.
- Maven wrapper는 현재 터미널에서 `Cannot start maven from wrapper` 오류가 발생하므로, 터미널 테스트 실행은 별도 보류한다.

## 3. 현재 패키지 구조

```text
web.mvc
├── advice
├── config
├── controller
├── domain
├── dto
│   ├── request
│   └── response
├── exception
├── jwt
├── repository
├── security
└── service
```

현재 컨트롤러는 `UserController`, `CustomerController`, `AdminController`로 구성되어 있다. 다만 `AdminController`는 아직 빈 컨트롤러이며, 채팅 전용 패키지와 컨트롤러는 아직 없다.

## 5. 도메인 구현 상태

### 5.1 User

현재 구현 필드:

- `userNo`
- `userId`
- `password`
- `userName`
- `role`
- `regDate`

구현 내용:

- `UserRepository.findByUserId(String userId)`로 로그인/회원 조회에 사용한다.
- 회원가입 시 비밀번호를 BCrypt로 암호화한다.
- 권한 값은 문자열로 저장한다. 테스트 코드에는 `ROLE_CUSTOMER`가 사용된 부분이 있고, 보안 정책 문서에는 `ROLE_USER`/`ROLE_ADMIN` 방향이 남아 있으므로 역할 명명 정책 정리가 필요하다.

### 5.2 Product

현재 구현 필드:

- `productNo`
- `productId`
- `productName`
- `price`
- `stock`
- `description`
- `regDate`
- `updateDate`

구현 내용:

- `ProductRepository`는 `JpaRepository<Product, Long>`를 상속한다.
- `findByProductId(String productId)`와 `findByProductName(String productName)`이 존재한다.
- 고객 상품 상세 조회는 현재 `productId`가 아니라 `productNo` 기준으로 조회한다.
- `ProductRes`는 고객 응답에서 `productId`를 노출하지 않는다.

### 5.3 Orders / OrderLine

현재 구현 필드:

- `Orders`: `orderNo`, `user`, `orderLines`, `orderDate`, `address`, `totalAmount`
- `OrderLine`: `orderLineNo`, `orders`, `product`, `unitPrice`, `quantity`, `amount`

구현 내용:

- 단건 주문 생성 시 상품 재고를 확인하고, 주문 수량만큼 재고를 차감한다.
- 주문 당시 가격을 `unitPrice`에 저장한다.
- 주문 금액은 `unitPrice * quantity`로 계산한다.
- `Orders.addOrderLine()`으로 양방향 연관관계를 연결한다.
- 주문 내역 조회는 `OrdersRepository.findAllByUserIdWithOrderLines(userId)`에서 주문 라인과 상품을 fetch join 한다.

### 5.4 Cart / CartItem

현재 구현 필드:

- `Cart`: `cartNo`, `user`, `cartItems`
- `CartItem`: `cartItemNo`, `cart`, `product`, `quantity`

구현 내용:

- `CartRepository.findCartsByUserId(userId)`에서 장바구니 항목과 상품을 fetch join 한다.
- 같은 장바구니에 같은 상품이 이미 있으면 새 항목을 만들지 않고 수량을 합산한다.
- 장바구니 주문 후 `cart.getCartItems().clear()`로 장바구니 항목을 비운다.

주의 사항:

- 현재 `createCartOrders()` 내부에서 각 `CartItem`의 상품이 아니라 `orderCreateReq.getProductNo()`로 상품을 다시 조회하고 있다. 장바구니 여러 상품 주문 시 같은 상품으로 처리될 수 있으므로 수정이 필요하다.
- `CartItem` 수량 합산 시 기존 수량과 추가 수량의 합계가 재고를 초과하는지 추가 검증이 필요하다.

### 5.5 Chat

현재 구현 상태:

- 채팅 도메인, Repository, WebSocket/STOMP 설정, 컨트롤러는 아직 구현되어 있지 않다.
- `ChatException`과 관련 에러 코드 일부만 준비되어 있다.

## 6. 현재 API 설계

### 6.1 인증/회원

| Method | URL | 설명 | 현재 상태 |
|---|---|---|---|
| POST/REQUEST | `/register` | 회원가입 | 구현 |
| POST | `/login` | 로그인 및 JWT 발급 | `LoginFilter` 기반 구현 |
| POST | `/logout` | 로그아웃 응답 반환 | 구현 |

정리 필요:

- `UserController.register()`는 현재 `@RequestMapping("/register")`와 `User` 파라미터를 직접 사용한다. 향후 `@PostMapping`과 요청 DTO 사용으로 정리하는 것이 좋다.
- 회원가입 성공 응답은 `ApiResponse.created(user)`를 사용하지만, HTTP 상태 코드는 현재 `200 OK`다. 실제 생성 의미를 반영하려면 `201 Created`를 검토한다.
- 로그아웃 메시지 문자열이 인코딩 깨짐 상태로 보이므로 수정이 필요하다.

### 6.2 고객 상품/주문/장바구니

| Method | URL | 설명 | 권한 | 현재 상태 |
|---|---|---|---|---|
| GET | `/api/products` | 상품 목록 조회 | 모두 허용 | 구현 |
| GET | `/api/products/{productNo}` | 상품 상세 조회 | 모두 허용 | 구현 |
| POST | `/api/orders` | 단건 주문 생성 | 인증 필요 | 구현 |
| GET | `/api/orders/me` | 내 주문 내역 조회 | 인증 필요 | 구현 |
| POST | `/api/cart/item` | 장바구니 담기 | 인증 필요 | 구현 |
| GET | `/api/cart/items` | 내 장바구니 조회 | 인증 필요 | 구현 |
| POST | `/api/cart/orders` | 장바구니 주문 | 인증 필요 | 구현, 보완 필요 |

기존 계획서와 달라진 점:

- 장바구니 담기 경로는 `/api/cart/items`가 아니라 현재 코드 기준 `/api/cart/item` 단수형이다.
- 상품 상세 조회는 `productId`가 아니라 `productNo` 경로 변수 기준이다.
- 별도의 `ProductController`, `OrderController`, `CartController` 없이 `CustomerController` 하나에 고객 API가 모여 있다.

### 6.3 관리자

| Method | URL | 설명 | 현재 상태 |
|---|---|---|---|
| POST | `/api/admin/products` | 상품 등록 | 미구현 |
| PUT | `/api/admin/products/{productNo}` | 상품 수정 | 미구현 |
| DELETE | `/api/admin/products/{productNo}` | 상품 삭제 | 미구현 |
| GET | `/api/admin/orders` | 전체 주문 조회 | 미구현 |
| GET | `/api/admin/sales/products` | 상품별 매출 통계 | 미구현 |
| GET | `/api/admin/users` | 회원 조회 | 미구현 |

현재 `AdminController`는 빈 컨트롤러이고, `AdminServiceImpl`도 `ProductRepository` 주입 외 로직이 없다. 다음 구현 순서는 관리자 상품 CRUD를 우선으로 잡는 것이 자연스럽다.

### 6.4 채팅

| Method/Protocol | URL/Destination | 설명 | 현재 상태 |
|---|---|---|---|
| POST | `/api/chat/rooms` | 고객 문의 채팅방 생성 | 미구현 |
| GET | `/api/admin/chat/rooms` | 관리자 채팅방 목록 조회 | 미구현 |
| GET | `/api/chat/rooms/{chatRoomNo}/messages` | 이전 메시지 조회 | 미구현 |
| WebSocket | `/ws` | STOMP 연결 엔드포인트 | 미구현 |
| SEND | `/pub/chat/rooms/{chatRoomNo}` | 메시지 발행 | 미구현 |
| SUBSCRIBE | `/sub/chat/rooms/{chatRoomNo}` | 채팅방 메시지 구독 | 미구현 |

채팅은 현재 프로젝트 코드 기준으로는 후순위 기능이다.

## 7. 서비스 계층 책임

| 서비스 | 현재 책임 | 비고 |
|---|---|---|
| `UserService` | 회원가입 | 로그인은 Spring Security 필터에서 처리 |
| `CustomerService` | 상품 조회, 주문 생성, 주문 내역 조회, 장바구니 담기/조회/주문 | 현재 고객 기능 대부분 담당 |
| `AdminService` | 미정 | 인터페이스와 구현체만 존재 |

기존 계획서에는 `ProductService`, `OrderService`, `CartService`, `ChatService` 분리가 있었으나 현재 프로젝트는 `CustomerService` 중심으로 구현되어 있다. 기능이 커지면 상품/주문/장바구니 서비스를 분리하는 리팩터링을 검토한다.

## 8. 보안 구현 상태

현재 `SecurityConfig` 정책:

- `POST /login`, `/register`: 모두 허용
- `GET /api/products`, `/api/products/**`: 모두 허용
- `POST /api/orders`, `/api/cart/item`, `/api/cart/orders`: 인증 필요
- `GET /api/orders/me`, `/api/cart/items`: 인증 필요
- Swagger 관련 경로: 모두 허용
- 그 외 요청: 인증 필요

보완 필요:

- 권한 정책은 현재 `hasRole` 기반의 고객/관리자 구분이 아니라 `authenticated()` 중심이다.
- 관리자 API가 구현되면 `ROLE_ADMIN` 접근 제어를 추가해야 한다.
- 고객 역할 명칭을 `ROLE_USER`, `ROLE_CUSTOMER` 중 하나로 통일해야 한다.
- WebSocket 인증은 아직 대상 코드가 없으므로 채팅 구현 시 별도 설계가 필요하다.

## 9. 트랜잭션 및 정합성 정책

현재 적용:

- 상품 조회와 주문 내역/장바구니 조회는 `@Transactional(readOnly = true)`를 사용한다.
- 주문 생성, 장바구니 담기, 장바구니 주문은 `@Transactional`을 사용한다.
- 단건 주문은 주문 생성과 재고 차감을 하나의 트랜잭션으로 묶는다.

보완 필요:

- 장바구니 주문 시 각 장바구니 항목의 실제 상품을 기준으로 재고와 금액을 계산해야 한다.
- 주문/장바구니 수량이 1 이상인지 검증하는 입력 검증이 필요하다.
- 상품 가격, 재고, 상품 ID 중복 검증은 관리자 상품 CRUD 구현 시 함께 정리한다.
- 현재 `ddl-auto=none`이므로 실제 DB 테이블 생성 SQL 또는 마이그레이션 전략이 필요하다.

## 10. 예외 처리 상태

현재 예외 구조:

- `DefaultExceptionAdvice`
- `ErrorCode`, `ErrorCodeProvider`
- `UserException`
- `ProductException`
- `OrderException`
- `CartException`
- `ChatException`
- `ErrorResponse`

대표 에러:

| 상황 | HTTP Status | 현재/계획 메시지 |
|---|---|---|
| 인증 실패 | 401 | 로그인 필요 |
| 권한 없음 | 403 | 접근 권한 없음 |
| 사용자 없음 | 404 | 사용자 없음 |
| 상품 없음 | 404 | 상품을 찾을 수 없음 |
| 주문 없음 | 404 | 주문을 찾을 수 없음 |
| 장바구니 비어 있음 | 400 | 장바구니가 비어 있음 |
| 재고 부족 | 409 | 상품 재고 부족 |
| 상품 ID 중복 | 409 | 상품 아이디 중복 |

보완 필요:

- 일부 로그/응답 문자열의 한글 인코딩 깨짐을 수정한다.
- 요청 DTO 유효성 검증과 `@Valid` 기반 입력 오류 응답을 추가한다.

## 12. 다음 작업 우선순위

### 12.1 고객 기능 안정화

- `createCartOrders()`가 각 `CartItem.product`를 사용하도록 수정

- 주문/장바구니 요청 DTO에 수량, 주소 필수 검증 추가
- `CustomerTests`에 장바구니 관련 테스트 추가

### 12.2 인증/보안 정리

- 역할 명칭을 `ROLE_USER` 또는 `ROLE_CUSTOMER` 중 하나로 통일

## 14. 구현 시 주의사항

- `UserRepository.findByUserId`처럼 JPA 기본 `findById(Long id)`와 충돌하지 않는 명명 규칙을 유지한다.
- `Product.productId`는 내부 상품 코드이고, 고객 응답에는 `productNo`와 상품 표시 정보만 제공한다.
- `Orders`는 SQL 예약어와 혼동될 수 있으므로 실제 테이블명 지정 여부를 검토한다.
- `application.properties`의 DB 계정과 Docker Compose 기본 계정이 현재 다르므로 정리한다.
- JWT secret은 운영 환경에서 코드에 고정하지 않고 환경 변수로 분리한다.
- 현재 문서에 남아 있는 관리자/채팅 계획은 아직 구현 완료가 아니므로, 완료 여부를 문서에서 명확히 구분한다.

## 15. 완료 기준

- 고객 상품/주문/장바구니 API가 IntelliJ 테스트와 Swagger에서 재현된다.
- 관리자 상품/주문/매출/회원 API가 구현되고 권한 검증이 통과한다.
- 채팅 메시지가 실시간 전달되고 DB에 저장된다.
- 인증 실패, 권한 실패, 상품 없음, 재고 부족, 장바구니 비어 있음 등의 예외가 명확한 HTTP Status와 응답 메시지를 반환한다.
- 실제 DB 스키마, Docker 실행 방법, 테스트 실행 방법, 배포 절차가 문서화된다.
